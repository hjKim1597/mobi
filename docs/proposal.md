## 1. 앱 한 줄 소개

차량의 주행 상태와 내비게이션 경로를 읽고, 운전자의 일정·메일·메신저를 지금 상황에 맞는 길이로 음성으로 알려 주고, 확인을 받은 뒤 대신 처리하는 인카 AI 비서.

---

## 2. 기획 배경

**운전 시간은 업무와 일정이 끊기는 시간이다.**
출근길에는 첫 회의가 몇 시인지, 밤사이 급한 메일이 있었는지 확인하지 못한 채 출발한다. 외근이 잦은 직장인은 이동하는 동안 고객 메일과 팀 메신저에 답하지 못하다가, 주차한 뒤 한꺼번에 처리하거나 신호 대기 중에 휴대폰을 집어 든다. 운전 중 휴대전화 사용은 도로교통법 제49조 제1항 제10호로 금지돼 있다. 정차 중이거나 안전운전에 지장이 없는 장치를 이용하는 등 법정 예외는 있지만, 확인하고 싶은 욕구는 사라지지 않는다. 통계청에 따르면 통근자는 하루 평균 73.9분을 출퇴근에 쓰고(2024), 국토교통부·한국교통안전공단 조사에서 운전 중 스마트기기 미사용 준수율은 64.32%였다(2025, 약 36%는 이 준수율을 100에서 뺀 값).

**기존 음성비서는 "물어봐야" 답한다.**
휴대폰 음성비서를 차에서 쓰려면 운전자가 먼저 무엇을 확인할지 떠올리고 말해야 한다. 정작 필요한 정보(10시 회의에 늦을 것 같다는 사실 등)는 운전자가 묻기 전에 알려 줘야 의미가 있다. 반대로 원하지 않을 때 계속 말을 거는 비서는 운전을 방해한다.

**차는 이 판단에 필요한 정보를 이미 갖고 있다.**
차량은 지금 주행 중인지 정차 중인지, 목적지가 어디이고 몇 분 뒤 도착하는지 알고 있다. 모비는 이 차량 맥락과 운전자의 업무 도구를 연결해 "언제, 얼마나, 무엇을 말할지"를 스스로 정한다.

**Gleo와의 역할 분담.**
Pleos의 Gleo AI가 차량과 차 안 경험을 다룬다면, 모비는 운전자의 메일·일정·메신저를 다룬다. 모비는 Gleo Interface(App Schema)로 기능을 노출해, 운전자가 "글레오, 모비로 오늘 일정 알려줘"처럼 Gleo를 통해서도 부를 수 있게 한다(2차 PT 전 연동 예정).

## 3. 앱 주요 기능 및 차량 특화 요소

| 기능 | 내용 | 차량 특화 요소 | 상태 |
|---|---|---|---|
| **출발 노크** | 출발할 때 오늘 첫 일정과 급한 메일을 한 문장으로 알린다. "오늘 10시 디자인 리뷰가 있고, 급한 메일이 1건 있어요. 들어보실래요?" | 차량 시스템 부팅과 10분 이상 P 정차 후 D 전환으로 새 트립 감지 | 구현(일정) |

| **지각 예측 알림** | 도착 예정 시각이 다음 일정 시작 시각보다 늦으면 먼저 알리고 대처를 제안한다. "10시 회의에 7분 늦을 것 같아요. 참석자에게 늦는다고 메일 보낼까요?" | 내비 ETA와 캘린더 일정 비교. 모바일 단독으로는 어려운 기능 | PT 전 구현 |
| **음성 승인 대행** | 메일 답장, 일정 변경, Slack 답장을 대신 작성하고 요약을 읽어 준 뒤 "보내" 같은 짧은 확인을 받고서만 실행한다. 명시적인 승인 후 10초간 실행을 유예하고, 그동안 "취소"로 중단할 수 있다. | 주행 중에는 요약만 읽고, 전문은 정차 후 화면 카드로 확인 | PT 전 구현 |
| **주행/정차 적응형 화면** | 주행 중에는 화면 조작 없이 음성만 사용하고 화면에는 상태 표시만 둔다. 정차하면 오늘 일정, 처리 대기 항목, 메일 요약을 카드로 보여 준다. | `CarUxRestrictions`와 기어를 함께 확인. P이고 안전 제한이 없을 때만 화면 조작 허용 | 일부 구현 |
| **도착 전 리마인더** | 목적지에 가까워지면 그곳에서 할 일을 알린다. "사무실 도착하면 견적서 회신해야 해요." 주차하면 카드로 다시 보여 준다. | NaviHelper 남은 거리·도착 이벤트 | PT 전 구현 |
| **동승자 배려** | 조수석에 사람이 타 있으면 메일 본문을 소리 내어 읽지 않고 "○○님 메일 1건" 수준으로만 알린다. | Vehicle SDK Seat 도메인의 좌석 착석 감지 | PT 전 구현 |

**안전 원칙**
- 주행 중에는 터치, 키보드, 긴 텍스트를 쓰지 않는다.
- 외부로 나가는 행동(발송·변경)은 반드시 음성 확인을 받고, 응답이 모호하면 실행하지 않는다.
- 계정 연결처럼 설정이 필요한 작업은 정차 중에만 허용한다.

## 4. 주요 사용 시나리오

아래는 완성 제품의 이용 흐름이며, 현재 빌드는 일정 관련 부분을 제공한다(구현 범위는 5번 참고).

**시나리오 1. 외근 영업 담당자의 오전 이동** (주 타깃)

1. 08:40 출발. 모비: "오늘 첫 일정은 10시 강남 고객 미팅이에요. 급한 메일이 1건 있는데 들어보실래요?" → "응."
2. 남은 시간 35분. 모비가 급한 메일(견적 일정 문의)을 요약해 읽고 "다음 주 화요일 가능하다고 답장할까요?"라고 제안 → "그래, 화요일 오후로." → 모비가 답장 요약을 읽음 → "보내." → 명시적인 승인 후 10초간 유예, 취소가 없으면 발송.
3. 정체로 도착 예정이 10:07로 늘어남. 모비: "10시 미팅에 7분 늦을 것 같아요. 고객에게 늦는다고 메일 보낼까요?" → "보내 줘."
4. 도착 3분 전. 모비: "미팅 자료는 어제 Slack에서 팀장님이 공유한 파일이에요."
5. 주차. 화면에 오늘 남은 일정과 방금 보낸 메일 2건이 카드로 표시된다.

**시나리오 2. 조용히 가고 싶은 퇴근길**

1. 18:30 출발. 모비: "내일 9시 주간회의가 있어요. 더 들으실래요?" → "됐어, 조용히 가자."
2. 모비는 바로 멈추고 이번 이동이 끝날 때까지 먼저 말을 걸지 않는다.
3. 20분 뒤 운전자가 먼저 부른다. "모비, 내일 회의 몇 시였지?" → 그 질문에만 답한다.

**시나리오 3. 동료와 함께 이동할 때**

1. 조수석에 동료가 탄 채로 출발. 모비는 좌석 착석 감지로 동승자가 있다는 걸 안다.
2. 모비: "급한 메일이 1건 있어요. 내용은 정차하면 화면으로 보여 드릴게요."
3. 정차하면 카드로 메일 요약을 확인한다.

## 5. 개발 계획

**현재 구현 범위**: 일정 기반 출발 노크와 남은 시간 맞춤 브리핑, 정해진 짧은 거절 응답과 트립별 묵음, 주행/정차 화면 전환과 일정 카드다. Google Calendar 읽기 전용 QR 연결, 당일 캐시를 이용한 오프라인 노크, 가상 일정 데모도 제공한다. 3번 표의 두 "구현(일정)"과 두 "일부 구현"은 이 범위를 뜻한다.

**PT 전 구현 예정**: 출발 노크·브리핑을 메일·메신저로 확장하고, 자유로운 거절 문장과 묵음 중 재호출 응답, 메일·처리 대기 카드를 추가한다. 지각 예측, 명시적 승인 후 10초 유예하는 대행, 도착 전 리마인더, 동승자 배려와 Gleo 연동도 구현할 계획이다. 3번 표의 "PT 전 구현" 네 항목과 일부 구현 기능의 나머지 범위에 해당한다.

### 5-1. 구조

차량 앱은 차량 상태 인식과 안전 판단을, 서버는 음성 처리와 외부 서비스 연동을 맡는다. 현재 서버는 일정 읽기만 제공하며 발송·변경 도구를 노출하지 않는다. 2단계 대행에서는 서버가 행동을 제안하고 주행 상태를 아는 차량 앱이 실행 승인을 받도록 확장할 계획이다.

```
┌──────────── 차량 앱 (Kotlin, Pleos Connect) ─────────────┐
│ 차량 상태: CarUxRestrictions, 기어                         │
│ 경로 상태: NaviHelper 남은 시간, 경로 종료·도착 시 초기화   │
│        ↓                                                  │
│ 대화 상태머신 × 주행 상태 → 안전 게이트                     │
│ 음성: STT/TTS 교체형   화면: 주행=상태 표시 / 정차=카드      │
└───────────────────────┬──────────────────────────────────┘
                        │ HTTPS
┌──────────── 모비 서버 ────────────────────────────────────┐
│ AI: STT·TTS, 일정 질문 분류, 남은 시간별 일정 브리핑        │
│ 연동: Google Calendar 읽기 전용                            │
│ 계정: OAuth 토큰 암호화 보관                                │
└──────────────────────────────────────────────────────────┘
```

**대화 상태**: 현재는 대기 → 노크 → 응답 대기 → (거절) 이번 트립 묵음 / (수락) 브리핑 → 대기이며, 시간 초과·오류 때는 보류한다. 승인 대기 → 실행과 도착 전 리마인더는 2단계에서 추가할 계획이다.
대화 상태와 주행/정차 상태는 따로 관리하고, 두 상태를 함께 보고 무엇을 말하고 보여 줄지 정한다.

**음성 계층**: 음성 입출력을 교체할 수 있게 분리했다. 현재 앱 녹음 → 서버 인식 → 음성 파일 재생 경로를 사용한다. Cloudflare Workers AI의 `whisper-large-v3-turbo`로 한국어를 인식하고, 확인 응답에는 어휘 힌트를 준다. 예비 STT 요청에는 `whisper`를 사용한다. 일정 질문의 일반 경로는 `gpt-oss-20b`의 낮은 추론 설정을, 합성은 MeloTTS의 `lang=kr`을 사용한다. 정형 일정 질문 5종에는 틀 답변 경로가 있고, 브리핑 음성은 캐시해 재사용한다. Pleos STT/TTS가 정식 제공되면 교체 비교할 예정이다.

**스파이크 측정 결과**: 2026년 10월 23~24일 짧은 한국어 응답에서 Pleos 온디바이스 STT는 20건 중 9건, 실제 목소리와 어휘 힌트를 사용한 서버 STT는 20건 중 18건을 맞혔다. 서버 STT의 잘못된 SEND/CHANGE 분류는 0건, 처리 시간 p50은 1.7초, 최대는 10.9초였다. 작은 표본의 결과이며 실차 주행 소음·여러 화자에서의 정확도를 보장하지 않는다. LLM 도구 선택은 한국어 20턴 중 20턴, 첫 문장 생성 p50은 0.69초였고, MeloTTS는 청취 10건 중 10건 확인, 생성 p50 0.70초였다.

**지연과 남은 검증**: 10월 24일 서버 측 확인 응답 p50 1.53초, 브리핑 1.30초, 질문 3.73초였으나 질문 요청 20회 중 4회는 502 오류였다. 10월 25일 후속 측정에서 서버 질문은 4.1~4.4초였고 12회 중 4회가 4.8초를 넘었다. 앱의 짧은 대답 p50도 2.3초로 목표 2.0초에 미달했다. 두 측정은 조건이 달라 직접 비교하지 않는다. 현재 6초 데드라인·늦은 응답 폐기·단계별 예비 요청을 구현했지만, 변경 후 지연·오류율과 실차 마이크·클라우드 성능은 추가 검증 대상이다. 짧은 응답의 무음 종료 기준 0.4초, 예비 요청 1.0초, 질문 내부 기준 3.9초는 후속 계획이며 현재 앱의 확인 무음 종료 기준은 0.5초다.

**계정 연결**: 현재 P이고 안전 제한이 없을 때 차량 화면의 QR을 휴대폰 기본 브라우저로 열어 Google Calendar 읽기 권한에 동의한다. 차에서는 비밀번호를 입력하지 않고 OAuth 토큰은 서버에 암호화해 보관한다. Google OAuth와 서버 암호화 키 설정이 필요하다. Slack 연결, 운전자 변경 시 화면에서 로그아웃·계정 전환하는 기능은 2단계 계획이다.

### 5-2. SDK/API 사용 계획

| SDK / API | 용도 | 상태 |
|---|---|---|
| AAOS `CarUxRestrictions` | 주행/정차 판단, 화면 모드 전환 | 에뮬레이터 확인: P에서 제한 없음, D에서 제한 적용 |
| AAOS `CarPropertyManager` | 기어(P→D 출발 판단) | 에뮬레이터 확인 및 앱 구현. 주차 브레이크·차속의 앱 활용은 향후 계획 |
| Vehicle SDK – Seat | 좌석 착석으로 동승자 감지 (`SeatOccupancy`) | 스파이크에서 신호 확인, 앱 반영은 2단계 계획 |

## 6. 기대효과 및 발전 가능성

### 타깃 고객

| 구분 | 고객 | 모비가 필요한 순간 |
|---|---|---|
| 주 타깃 | 외근이 잦은 영업·현장 관리직 | 하루 여러 번 이동하며 고객 메일과 팀 메신저에 답해야 할 때 |
| 보조 타깃 | 자차로 출퇴근하는 직장인 | 출근길 첫 일정 확인, 퇴근길 내일 일정 확인 |
| 보조 타깃 | 1인 사업자·프리랜서 | 이동 중 고객 문의에 바로 답해야 할 때 |

### 사용자 가치

현재는 운전 중 화면 조작을 줄이면서 오늘 일정을 듣는 경험을 제공한다. 다음은 2단계 확장으로 검증할 기대효과이며, 실사용 성과를 측정한 결과는 아니다.
- 주차 후 몰아서 처리하던 메일·메신저 응대를 이동 중에 끝낸다.
- 지각을 미리 알고 상대에게 먼저 알린다.
- 운전 중 휴대폰을 집어 들 이유를 줄인다.

### 예상 MAU (추정 방식)

MAU = 국내 Pleos Connect 탑재 차량 수 × 앱 설치율 × 월 활성률

- 탑재 차량 수: 현대차그룹의 발표 목표는 2030년까지 약 2,000만 대(글로벌)이며, 신형 그랜저(2026.5)부터 적용된다. 현재 국내 보급 대수나 모비의 이용자 수가 아니다. 국내 비중은 공개 수치가 없어 자체 가정이 필요하며, 국내 보급 실적을 확인한 뒤 정할 예정이다.
- 설치율: 아직 측정값이 없다. 업무용 생산성 앱의 타깃 직군 비중을 반영해 자체 가정을 세우고, 초기 설치 전환율로 보정할 계획이다.
- 월 활성률: 반복되는 출퇴근이 재사용을 유도할 것이라는 자체 가정이다. 출시 후 실제 트립별 사용 빈도로 검증할 계획이다. 국내 비중·설치율·활성률의 수치가 정해지지 않아 현재는 숫자로 된 MAU 전망을 제시하지 않는다.

### Retention 전략
- **매일 쓰는 이유**: 당일 일정과 노크 음성이 캐시된 새 트립에서 먼저 안내한다. 부팅 후 음성 응답에는 앱 실행과 마이크 권한이 필요하며, 강제 종료 뒤에는 앱을 다시 열어야 한다.
- **떠나지 않게 하는 장치**: 원치 않으면 한마디로 조용해지는 매너 모드가 "귀찮은 비서"라서 지우는 이탈을 막는다.
- **측정 지표**: 노크 수락률, 이동당 처리한 대행 건수, D7/D30 리텐션을 출시 후 측정할 계획이다. 대행 건수는 2단계 적용 지표이며, 목표 수치와 실제 리텐션은 아직 없다.

### 수익 모델

아래는 도입을 검토하는 요금 구분이며, 현재 결제·구독 기능은 구현하지 않았다.
- 무료: 출발 노크, 일정 브리핑, 매너 모드
- 구독: 메일·메신저 승인 대행, 계정 여러 개 연결, 지각 예측 알림

### 서비스 확대 계획
1. **연동 확대**: Microsoft 365(Outlook·Teams), Notion 연동을 검토한다. iOS 동반 앱으로 Apple 캘린더·미리알림을 연결하는 방안도 장기 계획이다.
2. **법인 차량(B2B)**: 영업 차량 운영 회사에 팀 단위 구독을 제공하는 방안을 검토한다.
3. **공유 차량**: 렌터카·카셰어링에서 탑승 시 계정 연결과 하차 시 자동 로그아웃을 제공할 계획이다.
4. **해외**: 지역별 주행 규제 정책을 확인한 뒤 다국어 확장을 검토한다.
